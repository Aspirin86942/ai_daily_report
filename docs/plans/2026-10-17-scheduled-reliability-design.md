# 定时链路可靠性设计（子项目 A）

- 状态：待用户审查
- 日期：2026-10-17
- 范围：定时日报失败自愈、健康巡检、本地通知、调度日志补齐；不含备份、OCR、成本治理、日报内容改版
- 关联：[当前状态](../current-state.md)、[日报使用与恢复](../daily-report-operations.md)、[Windows 安装与回退](../windows-deployment.md)

## 一、背景与证据

2026-10-16、10-17 连续两次 09:00 定时日报失败，均靠当天手工恢复才发布：

| 日期 | 目标日 | 失败码 | 可核对证据 |
| --- | --- | --- | --- |
| 10-16 09:00 | 10-15 | `MODEL_COMPOSE_CAPACITY_INSUFFICIENT` | 运行 `8f373be8…` 无模型调用、无快照；同目标后续运行 `13c644b0…` 成功发布 |
| 10-17 09:00 | 10-16 | `MODEL_RESPONSE_INVALID` | 调用 721 失败（响应已保存）；同一冻结请求在 13:08 的人工恢复中重试成功（调用 722） |

其他已核实事实：

- 任务已配置 `RestartOnFailure`（2 次 / 15 分钟），但两次失败后均未观察到 09:15 的重试记录，不能依赖该机制。
- `append_scheduled_log` 失败时只写 `at/status/error_code`，缺 run_id、目标日期、阶段；采集成功条目 `date/quality` 为 null，无法从日志区分命令。
- 失败恢复依赖人工执行 `daily`（内部 `resume_pending` 会续跑冻结运行），机制本身有效，缺的是自动触发与告警。
- 归档日报来源下，重复执行已发布目标日会命中 `existing_archive`，快速返回且零模型调用；这为“多次兜底触发”提供了安全前提。

## 二、目标与非目标

**目标**

1. 单次模型响应无效或成稿容量不足不再导致整日报废：有界自动重试/拆分/降级，保留全部证据与账本。
2. 09:00 首次失败后，系统在当天内自动续跑，不依赖人工。
3. 每天自动巡检任务、采集连续性、日报发布、磁盘与数据库状态；异常时本机通知并留下健康文件。
4. 调度日志字段完整，足以事后定位一次失败。

**非目标**

- 不自动更换模型或解析器（保持现有原则）。
- 不新增备份功能（用户明确不需要）。
- 不改日报内容结构、不改扫描/解析范围、不启用 OCR。
- 不引入新模型调用预算强制（维持现状）。

## 三、总体方案（已选）

三层自愈，按“应用内 → 宿主 → 观测”顺序：

1. **应用层**：模型响应无效做有界重试；成稿容量不足做拆分或降级待确认。
2. **宿主层**：同一 daily 任务在 09:30、10:30 各增加一次兜底触发；首次成功时兜底触发快速返回、零模型调用。
3. **观测层**：新增只读 `health` 命令与独立健康任务（11:00 与 23:00），异常时 Windows 本地通知 + 健康文件。

备选方案与取舍：

- 只用 PowerShell wrapper 包裹任务并在脚本里 sleep 重试：受 20 分钟执行上限与窗口影响，退出码语义也会变化，不采用。
- 只依赖任务计划器 `RestartOnFailure`：未观察到实际生效，且无法覆盖“失败后需重新规划”的场景，不采用。
- 只加应用内重试：无法覆盖进程级失败与“整次未启动”，不采用。

## 四、详细设计

### A1 模型响应无效的有界重试

- 位置：`report_app/src/model/mod.rs` 执行循环。
- 规则：`MODEL_RESPONSE_INVALID`（结构、schema、引用、长度等校验失败）视为可重试，最多追加 `llm.invalid_response_retries` 次（新配置，默认 1，范围 0–2）；仍受单次运行截止时间与 `max_retries` 总尝试约束。
- 每次尝试独立写账本与请求/响应快照；重试复用同一请求字节与请求指纹；最终失败保留原错误码与全部响应证据。
- 不重试的错误：HTTP 4xx（除既有 408/429/5xx 规则）、输入/配置/权限类错误。
- 容量类错误（`MODEL_COMPOSE_CAPACITY_INSUFFICIENT`、`MODEL_OUTPUT_TRUNCATED`、`MODEL_FACT_*`）不在此重试，走 A2 拆分。

### A2 成稿容量不足的拆分与降级

- 复现：用冻结输入与合成事实复现 `MODEL_COMPOSE_CAPACITY_INSUFFICIENT` 的触发条件，重点覆盖 `compose_groups` 中“单条事实/单组无法装入请求”的边界；实现阶段先给出复现证据。
- 修复顺序：先把该组事实按条二分交给现有 `execute_complete` 拆分；单条事实仍放不下时，剥离表头/上下文重试；仍不行则把该事实降级为待确认（保留原文、来源与 `matter_id`），不阻塞整份报告。
- 事实全覆盖约束保持：每个 fact_id 必须出现在正文或待确认；降级事实写入待确认并记录 `MODEL_COMPOSE_CAPACITY` 覆盖说明（不改变事实原文与引用）。
- 连续拆分次数设上限，超限按最佳努力保留其余内容并输出明确错误，不静默丢弃。

### A3 定时任务兜底触发

- `task plan` 与安装/检查脚本为 daily 任务增加两个触发器：09:30、10:30（同日历日，单实例 `IgnoreNew`）。
- 首次 09:00 成功后，09:30/10:30 触发命中“已发布”或“无待续运行”，应在 2 秒内返回、零模型调用；实现时以测试证明。
- 首次失败但进程已退出时，09:30 触发经 `resume_pending` 续跑冻结输入；09:30 仍失败则 10:30 再试一次。
- 任务 action 不变（仍直接执行 EXE），避免包装脚本带来的窗口与退出码问题；`RestartOnFailure` 保留但不作为主要手段。
- 兜底触发导致的重复尝试在报告中可见（运行记录、账本）；不重复发布、不覆盖人工修改。

### A4 健康巡检命令

新命令：

```text
ai-daily-report.exe --config-dir <dir> health [--target-date YYYY-MM-DD] [--format json|text]
```

默认目标日为上一自然日；只读，零模型调用，不扫描原目录，不改数据库。

检查项与判定：

| 检查 | 判定 | 级别 |
| --- | --- | --- |
| 采集连续性 | 目标日 00:00–24:00 每 30 分钟一条已完成采集，允许 ±60 秒；基线前时段标注 `BASELINE_WINDOW` 不判故障 | error |
| 日报发布 | 报告库存在该日 `published` 运行，且 `reports/<YYYY-MM>/<date>.md` 存在、哈希与数据库正文一致 | error |
| 未完成/失败运行 | 待续运行数 > 0，或近 24 小时失败运行存在 | warning |
| 解析队列 | 归档库未完成解析数 > 0 | warning |
| 磁盘 | `data_dir` 所在卷剩余 < 20 GiB warning，< 5 GiB error | warning/error |
| 数据库 | 报告库与归档索引 `PRAGMA quick_check` 通过 | error |

输出：JSON 含 `status`（healthy/warning/unhealthy）、`checks[]`（code/level/message/证据）、`target_date`、`generated_at`；文本为逐行摘要。退出码 0/1/2。

### A5 健康任务、健康文件与本地通知

- 新增任务 `AI Daily Report Health`，每日 11:00、23:00 触发（避开 10:30 兜底触发的 20 分钟执行窗口），动作调用发布包内 `scripts/health_notify.ps1`（Windows PowerShell 5.1 兼容，`-NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden`）。
- 脚本职责：调用 `health` 命令取 JSON；用 `Get-ScheduledTask`/`Get-ScheduledTaskInfo` 回读 daily 与 collect 任务并合并；写 `logs/health-YYYY-MM-DD.json`；非 healthy 时弹出托盘气泡通知（`System.Windows.Forms.NotifyIcon`），并写 `logs/health-notify.log`；`-NoNotify` 供测试。
- 通知内容：目标日、结论、首个失败检查码、建议命令（如 `daily --target-date`）；同日同码只通知一次。
- 健康文件始终写入（无论健康与否），作为本机可审计记录；不写入报告库、不进入归档。

### A6 调度日志补齐

`append_scheduled_log` 统一输出：

```json
{"at":"…","kind":"daily|collect|health","status":"succeeded|failed","run_id":"…","target_date":"…","phase":"…","quality":"…","error_code":"…","duration_ms":123}
```

- 失败也写 run_id（若已创建运行）与阶段；collect 条目写 `kind=collect`、`run_id`，`target_date` 为 null。
- 追加字段向后兼容，不改变现有 JSONL 解析方式。

## 五、错误处理与边界

- 自动重试/续跑全部有界：受 `llm.max_retries`、`llm.invalid_response_retries`、运行截止时间、任务执行上限约束；超限按失败处理并保留证据。
- 重试不改变请求身份：同一请求字节、同一指纹；账本按尝试记录，恢复时只复用成功响应。
- 健康检查本身失败（如数据库打不开）按 unhealthy 处理并输出原因，不静默。
- 首次基线日（2026-10-17）采集起点前的时段标记为基线窗口，不判故障；此后按正常规则。
- 本机通知在锁屏/未登录时可能不显示，健康文件与日志兜底。

## 六、测试与验收

实现阶段（隔离目录、固定样本、本地 HTTP 模拟，0 次真实模型调用）：

1. 响应无效：第一次返回无效 JSON/引用，第二次有效 → 断言自动重试成功、账本 2 条、快照完整；两次无效 → 失败且保留 2 份响应。
2. 成稿容量：构造超限事实组 → 断言拆分后全部事实出现；单条超限 → 断言降级待确认并保留原文。
3. 兜底触发：受控失败后第二次执行 → 断言续跑成功；已发布后再次执行 → 断言 <2 秒、0 模型调用、无重复发布。
4. health：6 类故障各 1 个 fixture（任务缺失、采集缺口、日报缺失、磁盘阈值、运行失败、DB 损坏），断言退出码与 JSON。
5. 通知脚本：`-NoNotify` 模式下断言健康文件与去重文件写入。
6. 门禁：`cargo fmt --all -- --check`、`cargo clippy --workspace --all-targets --locked -- -D warnings`、`cargo test --workspace --locked`；发布包清单校验。

上线验收（10-18 首份归档日报验收完成、用户另行授权部署后）：

- 受控失败演练一次（隔离任务名），确认 09:30 兜底与通知。
- 连续 2 个自然日观察：09:00 真实触发、健康任务输出、健康文件齐全；不额外触发模型请求。
- 保留原任务 XML、原包与原配置；回退按 [Windows 回退说明](../windows-deployment.md)。

## 七、部署与回退

- 新功能进入新版本发布包（`.releases/rust-<日期>-reliability-01`），不动当前 `archive-05` 生产包；构建与包校验按 `scripts/build_windows_release.ps1`。
- 任务变更（daily 兜底触发 + 新 health 任务）需显式授权：先 plan 后 Apply，保存原 XML，注册后回读比对；不符合计划则禁用并报错。
- 回退：恢复保存的任务 XML 与旧版本指针，保留新增健康文件、日志与运行记录，不覆盖业务数据。

## 八、风险与已定决策

| 风险 | 处理 |
| --- | --- |
| 自动重试增加模型调用（用户已表示成本不重要） | 上限 1–2 次，账本可查；失败仍明确报错 |
| 任务触发器变更影响 10-18 验收 | 验收完成前不部署，只做仓库内开发与本地验证 |
| 健康巡检误报（基线日、跨日采集） | 基线窗口豁免、允许 ±60 秒、历史缺口不判当日故障 |
| `MODEL_COMPOSE_CAPACITY_INSUFFICIENT` 根因未完全复现 | 实现第一步用冻结证据复现；若无法复现，按边界修复并以单测锁定 |
| 本地通知可见性 | 健康文件 + 日志兜底，通知去重防刷屏 |

已定决策：

- `llm.invalid_response_retries` 默认 1（总尝试 2 次）；若冻结证据表明需要更多次，实现计划中修改并说明。
- 健康任务时间固定 11:00 与 23:00；如需调整在部署授权时同步。
- 通知渠道固定为 Windows 托盘气泡 + 健康文件，不接企业微信或邮件。
