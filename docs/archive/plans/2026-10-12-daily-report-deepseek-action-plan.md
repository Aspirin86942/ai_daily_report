## 1. 交付结果与审阅重点

交付一个 Windows 本地批处理程序：每天北京时间 09:00，整理工作目录内前一个自然日修改过的文件，向公司模型网关发送有限摘录，生成附来源、覆盖范围和缺漏说明的中文日报。报告长期保存在本机，运行失败可以恢复，已有模型结果可以复用。

### 1.2 本计划给出的实施默认值

| 决策 | 推荐值与效果 |

### 1.3 完成标准

- 指定日期能选中预期文件，报告标题、业务键、扫描窗口、文件名保持一致。
- 每条模型摘要引用有效来源，来源显示提取范围；文件内容不能被自动升级为已完成工作。
- 无候选且扫描完整时，零模型调用生成无变化报告；读取失败不能冒充无变化。
- 同一输入普通重跑复用已完成请求；数据库提交后的输出修复零模型调用。
- 在文件替换前后中断，恢复后产物完整；用户修改过的主文件受到保护。
- 旧日报可读，周报和月报能正确消费新旧报告，包含确实存在的周末日报。
- Windows 任务可安装、检查、禁用和移除，读取回的配置与本计划一致。
- 连续 3 个真实计划日有可核验的触发、运行和产物记录；这一运行证据与离线测试分别报告。

## 3. 总体流程与职责

```text
Windows 09:00 / 登录后检查 / 手动命令
  -> 冻结日期、读取配置、获取跨进程锁
  -> 优先恢复已提交产物或已有输入的中断任务
  -> Rust 发现文件、日期筛选、稳定性检查、有界解析
  -> 来源清单、覆盖信息、输入快照、模型请求计划
  -> 公司网关 deepseek-flash；逐请求持久保存结果
  -> 本地结构与来源校验
  -> 报告库提交正文、完整 Markdown 和预期校验和
  -> 同目录临时文件、原子替换、发布检查点
```

Python 负责业务日期、模型请求、恢复编排和报告发布。Rust 继续负责文件发现、解析、缓存、提取预算和来源证据。模型只接收有限资料并返回结构化摘要，不拥有文件操作、命令执行或任意联网工具。

`ReportRunner` 作为单次流程入口。新增功能按日期、运行存储、模型请求、发布职责拆分；复用现有 `NativeScanner`、`SQLiteStore`、`LLMClient`、`ReportGenerator`。目录数量当前固定为一个，不引入多租户或多个扫描范围的调度系统。

## 4. 日期、命令与兼容规则

### 4.1 日期一次解析，全程传递

新增不可变的 `RunContext`，包含 `run_id`、`scope_id`、`target_date`、`timezone`、`window_start_utc`、`window_end_utc`、配置版本和启动时间。日期、模型和解析层均消费这份上下文，不重新计算今天。

例如 2026-10-12 09:00 执行：报告日为 2026-10-11，窗口为北京时间 `[2026-10-11 00:00, 2026-10-12 00:00)`，对应 UTC `[2026-10-10 16:00, 2026-10-11 16:00)`。

Python 使用 `zoneinfo.ZoneInfo` 与可用的 `tzdata`；Rust 按绝对时间比较文件 `mtime`。时间窗、时区与选择策略版本纳入扫描和上下文缓存身份，避免复用旧的本地日期筛选结果。

### 4.2 拟交付命令

| 命令 | 行为 |
| --- | --- |
| `daily` | 手动生成前一个自然日的证据日报；不等待交互输入 |
| `daily --target-date YYYY-MM-DD` | 生成指定自然日；历史日期明确显示实际观察时间 |
| `daily --scheduled` | 计算最近已到 09:00 交付时间的业务日，并执行恢复与重复检查 |
| `daily --dry-run --target-date YYYY-MM-DD` | 本地发现、提取、覆盖检查；输出本地预检清单，不构造模型客户端，不发布正式日报 |
| `daily --no-save` | 允许模型生成预览；不更新当前正式日报或主 Markdown；请求预算和恢复审计仍保存 |
| `daily -i "补充事实"` | 将明确用户陈述作为独立来源纳入模型输入与指纹 |
| `daily --target-date YYYY-MM-DD --regenerate --reason "原因"` | 显式开启新的生成轮次；保留旧产物和诊断，沿用调用限额 |
| `repair-output --target-date YYYY-MM-DD` | 使用已存完整 Markdown 修复输出；不扫描、不调用模型、不依赖原始输入快照 |
| `runs --target-date YYYY-MM-DD` | 显示阶段、质量、错误码、调用计数和产物位置；不输出正文和密钥 |
| `doctor --strict` | 本地运行时、契约、路径、worker、凭据存在性检查；不发模型请求 |
| `doctor --check-model` | 实施阶段用合成文本验证指定网关与模型，计入请求预算 |

预检允许更新扫描索引和生成 `.artifacts/preflight/` 下的本地清单；正式报告库内容和日报主文件保持不变。预检不要求模型凭据。

### 4.3 兼容与追赶

- `--date` 和 `--target-date` 同时出现时拒绝。单独使用 `--date` 时显示弃用提示，并采用统一目标日期语义。原有“只改标题日期”的调用行为发生变化，更新帮助、测试和迁移说明。
- 新的 `daily` 默认前一个自然日。旧日报记录原样保留。`--no-save` 的“可外发”含义保留；其预算审计写入必须在帮助中说明。
- `--scheduled` 与显式日期、`--no-save`、`--dry-run`、`--regenerate` 互斥。当天 09:00 之前登录时，最近到期目标日是前天；09:00 之后是昨天。
- 应用锁内优先处理已提交未发布的记录，再恢复已有输入快照的中断任务，最后检查本次到期目标日。跨午夜重启继续使用持久化目标日。
- 多日遗漏仅为最新到期日新建扫描任务；其他日期列入缺口。已持久保存输入的旧任务可基于原快照恢复，并披露观察时间。
- 成功报告的普通重跑先用新的本地来源指纹判断是否变化；输入未变时只检查或修复输出。完成后的重新扫描只生成新的观察记录，不使原报告的生成时间变化。

## 5. 扫描、来源和覆盖

### 5.1 文件选择

默认支持 `.docx`、`.xlsx`、`.xls`、`.pptx`、`.pdf`、`.txt`、`.md`、`.csv`。保留现有对应解析实现，`.doc`、`.ppt` 等旧格式保持显式启用；默认不采集 `.json`、`.log`。

固定排除本程序数据、报告、快照和日志目录，以及 `.git`、`.venv`、`.uv`、`node_modules`、`target`、`__pycache__`、临时目录、Office 锁文件、凭据文件。排除检查按路径组成部分进行，不用容易误伤普通文件名的子串匹配。

只处理目标根目录内的文件。规范化路径、大小写与根目录别名 `work`；同一路径重复出现合并，不同路径同内容保留各自来源，可共享解析结果。候选资格由日期决定，缓存命中不删除当日来源。

本次以整个 `D:/01- 工作` 为已选择根目录。上线预检列出实际候选与排除结果，便于发现需要明确排除的业务子目录；不宣称扩展名规则可以自动识别全部敏感材料。

### 5.2 云目录与链接

- 根据重解析标签识别符号链接、目录联接、云同步目录和未知类型，禁止“一见 ReparsePoint 就跳过”的处理。
- 默认不跟随符号链接与目录联接；读取前后校验实际路径仍在根目录内。未知重解析类型产生诊断。
- 允许枚举已选云同步根目录及已在本地的内容；不能因为根目录的 Cloud Files 标签跳过整个范围。
- 文件需要在线下载或目录枚举需要云端回填时，默认不主动触发下载；记录 `cloud_unavailable` 和受影响范围。`Pinned` 标记不能单独证明数据已完整落地。
- 不修改“始终保留在此设备”等同步属性。用户需要补齐本地文件时，由用户通过原同步工具处理后重跑。

Windows 文件属性及回填标志以 [Microsoft 文件属性说明](https://learn.microsoft.com/en-us/windows/win32/fileio/file-attribute-constants) 为依据；在真实目标目录验证标签处理，不能只靠普通临时目录测试。

### 5.3 解析与稳定性

复用现有有界解析器、来源保护和全内容哈希函数。候选文件在大小上限内计算内容指纹；对超限文件只记录跳过原因，不为计算哈希绕过文件大小和运行时间上限。

读取前后比较文件身份、大小、mtime 和现有来源保护标记；变化时最多额外尝试 1 次，仍不稳定则跳过。文件超过最大体积、解析超时、损坏、加密、读取失败分别记录。

保持现有解析预算作为本次明确上限：PDF 5 页、Excel 50 行、文本每文件 6000 字符、单文件最大 50 MiB；总模型输入另受第 6 节预算限制。CSV 保留现有前三行样本并明确标注。报告中的统计结论不能超出实际提取范围。

统一来源状态：`extracted`、`truncated`、`excluded`、`unsupported`、`unreadable`、`unstable`、`timeout`、`cloud_unavailable`、`failed`。正文提取、上下文压缩和模型输入阶段的截断分别记录，未知总页数或总行数使用空值。

### 5.4 契约增量

`ScanRequest` 增加成对可选的 UTC 起止边界；新版日报必须传入，旧调用不传时保持现有接口兼容。提供边界时验证其与显示日期一致，扫描使用半开绝对时间窗。周报、月报扫描路径也传入明确边界。

`ScanResult` 增加结构化 `sources`，从已有内存解析结果和审计证据构造，包含稳定来源键、相对路径、mtime、观察时间、内容指纹、实际摘录、解析后端、执行通道和覆盖标记。调用方不反向拆解 `file_context` 文本，也不重新打开扫描库拼接证据。

当前报告范围固定为 `scope_id=personal_work`。范围内的 `source_id` 使用规范化相对路径的 SHA-256；报告输入指纹同时包含范围和扫描根目录，防止换目录时复用旧摘要。展示编号按排序分配。读取时间、随机运行 ID、缓存命中与耗时不参与内容身份。所有新增行为版本进入 Rust 归一化配置与缓存身份；扫描数据库仍维持 schema 3。

质量规则：全部候选成功且无遗漏为 `complete`；有可用来源但存在截断、跳过或扫描缺口为 `partial`；扫描完整且没有候选、没有供模型处理的用户陈述为 `no_changes`；没有可用证据且扫描或解析失败为 `unavailable`。用户陈述可以作为独立可用来源，但文件采集缺口仍保留。

## 6. 公司网关与模型调用

### 6.1 固定接入方式

继续使用 `llm.provider: deepseek` 分支，复用现有 OpenAI 兼容客户端。`base_url` 使用用户提供的根地址，SDK 在其下调用 `chat/completions`；不自行添加 `/v1`，不自动切换到其他域名或模型。

凭据沿用现有 `DEEPSEEK_API_KEY` 环境变量，内容是公司网关的 Virtual Key（虚拟密钥）。计划、示例、命令行和日志只出现变量名。实际密钥由用户通过受控的本机方式提供给运行账户；不在源码中设置，也不写入任务参数。

client = OpenAI(
    base_url="https://ai-gateway.fsdev.cn",
    api_key=os.environ["DEEPSEEK_API_KEY"],

OpenAI SDK 支持自定义地址、关闭自动重试和显式超时；这些能力只证明客户端可配置，不能证明公司网关的兼容性。[OpenAI Python SDK 官方说明](https://developers.openai.com/api/reference/python)

### 6.2 联调完成条件

网关路由、`deepseek-flash` 可用性、JSON 输出支持、上下文限制与实际费用尚未通过带认证请求验证。实施时用固定合成文本完成一次受控能力检查，业务正文不进入这一步。

检查内容：请求确实到达配置地址；模型 ID 被接受；`system` 与 `user` 消息可用；`response_format={"type":"json_object"}` 可用；返回值能通过 Pydantic 校验；token 用量和错误码能够读取。上下文长度与允许的输出上限需由网关控制台或正式接口资料确认，并记录在非敏感能力配置中。

若根地址路由不兼容或缺少上述能力，阶段停止并报告具体缺口。根据该网关正式接口说明修订配置后复验；不以静默降级到其他服务或另一模型通过验收。不要求网关必须支持 `/models`，不将该接口缺失等同于聊天接口不可用。

### 6.3 请求、分批与复用

- 固定规则通过 `system` 消息传入，来源通过独立 `user` 消息传入。模型输入只包含来源 ID、必要相对名称、mtime、目标窗口、有限正文和覆盖信息。
- 新增模型返回类型 `EvidenceSummaryData`：`summary_items`、`verification_items`；每条包含 `text` 与非空 `source_ids`。日期、路径、质量和计数由本地程序填充。
- 每个来源 ID 必须属于当前批次；无效引用、错误 JSON、输出截断都不能进入正式报告。只验证 ID 存在不能证明句子真实，因此同时设置合成事实核验样例和人工内容验收。
- 按稳定来源键排序，按段落或表格行划分文本块；单个完整请求的消息 JSON 最多 16000 个 UTF-8 字节，每批最多 8 个来源块，最多 8 个批次。超出的内容记录为未发送并使质量为 `partial`。
- 小输入只调用一次。分批结果在本地按确定顺序合并，保留来源和定位；仅合并文本与来源集合完全相同的重复条目。无需增加一次整篇模型合并调用。
- 本机输出预算为 8192 tokens，包含思考与最终输出。真实联调确认 2048 会被思考过程耗尽，8192 下已完成非空日报。用序列化消息的 UTF-8 字节数加 1024 作为保守输入估算，与已确认的容量核对；该估算不记作真实 token 用量，也不宣称适用于未知 tokenizer 的精确计数。能力未确认的其他部署仍禁止真实业务调用。
- token 用量优先记录网关返回值；缺失时保存为空并记录估算。未确认网关单价前不输出虚假的金额预算，以请求次数、文本体积和时间约束运行。
- 每个批次在调用前保存规范化请求和摘要哈希，成功后立即保存经过校验的响应。后续批次失败时复用已经成功的批次。

`input_fingerprint` 用于报告级复用，覆盖业务日期、UTC 窗口、稳定来源键、文件内容指纹、实际截取范围、解析与提示词版本、网关地址、模型 ID、生成参数、输入中的用户陈述。执行耗时、缓存命中、本次观察时间和随机 `run_id` 不进入指纹。

`request_fingerprint` 使用实际模型消息、模型参数与当前生成轮次计算。同一生成轮次跨进程恢复不变；显式 `--regenerate` 开启新轮次并记录原因。旧轮次中的请求不能冒充强制重新生成的结果。

### 6.4 重试与时间控制

| 情况 | 行为 |
| --- | --- |
| 连接失败、超时、408、429、暂时性 5xx | 每逻辑请求总计最多 3 次；按 Retry-After 或指数退避重试，计入所有上限 |
| 401、403、模型不存在、路由不存在、确定的参数错误 | 立即停止；不重复请求 |
| JSON 或来源校验失败、输出被截断 | 最多重试 1 次，仍包含在该逻辑请求的 3 次内；不把原始响应全文写日志 |
| 请求结果未知，例如发送后断电 | 标记 `unknown` 并保留已占用预算；明确存在重复计费可能 |
| 单次运行或当日累计预算耗尽 | 保存恢复状态并停止，不因任务计划重启而清零 |

应用是唯一重试所有者，SDK 设置 `max_retries=0`。正常分批调用也计入预算。每次真实发送前用短事务预占一次计数，避免进程终止后漏计；同一逻辑运行的 12 次上限跨自动重启累计，30 次上限按实际北京时间自然日统计并覆盖预览和联调。

每个网络请求、解析步骤、退避前检查剩余时间。应用 15 分钟预算属于协作停止机制；SDK 网络超时不等于绝对墙钟时限。任务计划程序在 20 分钟执行硬终止，下一次按持久状态恢复。预算耗尽不会无限自动追加额度。

## 7. 报告数据、旧数据兼容与留存

### 7.1 报告类型与输出

保留旧 `DailyReportData` 读取，新增 `EvidenceDailyReportData`，通过 `schema_version=2` 和 `report_kind=file_evidence` 明确区分。新模型包含日期、时间窗、质量、结构化摘要、待核实事项、来源清单、缺漏、生成时间及用户附注。

报告示例：

```text
# 日报 2026-10-11
生成时间：2026-10-12 09:03 +08:00
范围：work；目标窗口：10-11 00:00 至 10-12 00:00
质量：部分覆盖；已解析 6 份，截断 2 份，读取失败 1 份
说明：根据实际读取时的当前文件整理。

## 文件内容摘要
- 当日修改的方案文档包含接口说明。[S001]

## 待核实事项
- 记录提及上线安排，实际部署状态待确认。[S002]

## 来源与覆盖
- S001：项目A/方案.docx；修改时间；观察时间；实际提取范围

## 缺漏与异常
- 1 份文件未能读取；2 份文件仅提取部分内容。

- 原样合并本日期的独立附注文件。
```

附注默认使用 `data/report_notes/YYYY-MM-DD.md`，以受控文件大小读取并在本地追加。它不发送模型，变化只触发重新渲染；发布指纹纳入附注哈希和模板版本。`-i` 是主动送入模型的用户陈述，两者在帮助中说明。

修复命令重放已存发布版本，不读取新的附注或模板。普通重跑发现附注、模板变化时创建新的发布尝试，可复用模型结果。

### 7.2 报告库增量迁移

报告库继续使用 `data/db/reports.sqlite3`。迁移前用 SQLite 一致性备份接口生成备份并执行完整性检查，记录原文件与备份的 SHA-256；不直接复制正在写入且可能使用 WAL 的主文件。

| 存储位置 | 关键内容与约束 |
| --- | --- |
| `daily_reports` | 保留旧列和 `date` 唯一键；增加 `schema_version`、`report_kind`、`current_run_id`；新报告完整数据存 `raw_json` |
| `report_runs` | 冻结业务上下文、配置/输入/发布指纹、生成轮次、phase、status、quality、计数、错误码、完整报告 JSON、完整 Markdown、预期与上次发布校验和 |
| `report_run_sources` | 每个运行的稳定来源 ID、相对路径、mtime、观察时间、内容指纹、各阶段覆盖与快照引用；唯一键为运行与来源 ID |
| `report_model_calls` | 每个逻辑步骤的尝试记录、请求指纹、请求快照位置、响应快照位置、状态、用量、实际调用日期和耗时；成功响应可恢复 |
| `report_schema_migrations` | 仅管理本报告库的增量版本与完成时间；不复用扫描库版本号 |

新报告在旧的 `completed_work`、`work_summary`、`next_plan` 列中写空字符串，避免旧字段语义误导；当前应用按版本解析 `raw_json`。旧应用不能保证读取新报告，代码回退必须同时使用迁移前报告库备份，并保留新库副本供恢复。

当前业务键固定为 `scope_id=personal_work`、目标日期、`Asia/Shanghai`。沿用 `date` 唯一键的前提是单一范围和固定时区；程序拒绝在同一报告库切换成其他范围或时区。未来多范围需求单独迁移，不提前扩展当前主键。

一次短事务将最终报告 JSON、运行结果、完整 Markdown 和 `db_committed` 阶段保存到 `report_runs`。此时 `daily_reports` 仍指向上次已发布版本；文件核验完成后的短事务同时更新 `daily_reports` 和 `published`。这样，输出冲突不会提前改变周报、月报读取的当前报告。扫描、网络调用和文件写入期间不保持 SQLite 写事务。

### 7.3 周报、月报兼容

读取方法返回明确的新旧日报联合类型，`format_period_report_context` 分别格式化。旧日报保持原有“完成内容、工作小结、计划”段落；新日报携带来源、覆盖和待核实说明。

周报和月报的提示词必须保留“文件证据”和“用户确认事实”的区别，不将文件摘要自动填成已完成工作；无依据的计划保持为空。周期报告的现有输出结构保持兼容。

`get_yesterday_plan` 仅从旧类型读取已有计划；新版证据日报返回空计划。新版日报生成不把历史计划当作已完成事实。待发布的 `report_runs` 不进入正常周期汇总，只有发布检查点完成的当前记录可见。

日期范围查询纳入范围内所有实际存在的日报，包括周末。启用自动日报后的缺失日期按自然日计算；启用前的旧历史沿用工作日缺失口径。每个运行或报告记录生成时间，不能用回填日期伪装历史快照。

### 7.4 快照与清理

模型输入和可恢复响应的快照放在 `data/run_snapshots/<run_id>/`，不保存全量原始文件。清单写入来源身份、摘要哈希、版本与实际提取范围。模型复用依赖快照和经过校验的结果，不依赖可驱逐的扫描缓存。

已发布当前报告及来源元数据长期保留；原始摘录和中间响应保留 14 天。成功模型响应随原始快照清理后，当前完整报告仍可复用和修复。已终结、非当前且无依赖的历史尝试与其来源元数据保留 30 天。

清理只针对程序自有目录中已过期、无恢复依赖的产物；校验解析后的绝对路径始终位于该目录内。达到 512 MiB 上限时先执行符合规则的到期清理，仍不足则在发送模型前报容量错误。不得为腾出空间删除原文件、当前报告或未完成恢复需要的数据。

## 8. 并发、发布与崩溃恢复

### 8.1 单实例与持久状态

任务计划程序设置 `IgnoreNew`，应用另使用 Windows 跨进程文件锁，锁文件固定在报告库旁，使用标准库 `msvcrt.locking` 持有句柄。锁名由规范化报告库路径与 scope 确定，覆盖手动命令、定时命令、迁移与修复。

进程退出后操作系统释放锁。PID 和运行 ID 仅供诊断，不通过“锁文件存在”判断持锁，也不靠删除锁文件解除竞争。等待上限 5 秒，超时返回明确的已有任务运行状态。

持久状态分开记录：`phase` 表示最后可靠阶段，`status` 表示运行、失败、取消或成功，`quality` 表示覆盖质量。失败不覆盖已完成阶段。

```text
phase: created -> scanning -> prepared -> generating -> db_committed -> published
status: running / failed / cancelled / succeeded
quality: complete / partial / no_changes / unavailable
```

`prepared` 必须意味着输入快照、请求计划和校验和均已持久保存。每次重试只读取已冻结输入；重新扫描构成新尝试，不能覆盖原快照。

### 8.2 发布必须保存精确内容

先完成本地渲染并冻结生成时间、模板版本和附注版本，使用 UTF-8 无 BOM 与 LF 换行。数据库保存精确正文与 SHA-256，随后在目标目录写临时文件、刷新、关闭句柄并原子替换。校验主文件后才写 `published` 并切换当前报告。

日常输出使用 `data/reports/YYYY-MM/YYYY-MM-DD.md`。来源名称和模型文本经过 Markdown 转义，不能将模型文本当作路径或脚本执行。替换失败保留 `db_committed` 和必要恢复数据。

### 8.3 恢复判定表

| 发现的状态 | 恢复动作 |
| --- | --- |
| 尚未 `prepared` | 重新扫描并创建完整快照；旧尝试保留中断原因 |
| 已 `prepared`，部分请求成功 | 校验快照；复用成功步骤，继续未完成步骤 |
| 已收到响应，尚未持久保存即中断 | 标记调用结果未知，沿用预算；不能承诺不重复计费 |
| 已 `db_committed`，Markdown 缺失 | 使用已存精确正文写文件，零模型调用 |
| 主文件等于待发布的预期校验和 | 文件已成功，补记 `published`，零模型调用 |
| 主文件等于上次发布校验和 | 原子替换为待发布正文，零模型调用 |
| 主文件与新旧校验和均不同 | 判定冲突，保留主文件，将候选另存到 conflicts 目录并提示 |
| 首次发布却已存在未知主文件 | 同样按冲突处理，不能直接覆盖 |
| 输入快照丢失或校验失败 | 已提交报告照常可修复；未提交结果停止恢复，明确新建扫描尝试 |

检查主文件与替换之间仍可能发生外部编辑。替换前再次核验，替换已有文件使用能够同时保留被替换版本的 Windows `ReplaceFileW`，备份放在同卷的程序自有冲突目录；首次发布采用目标已存在即失败的原子移动。通过标准库 `ctypes` 做小范围封装，不新增全局工具。

替换后校验被替换版本是否等于已确认旧版本。若外部并发编辑落在最后检查与替换之间，保留捕获到的原文件和候选，标记冲突，不推进当前报告。日常事前发现的手改保持主文件原样；极窄竞争窗口中的原内容以副本保护并明确提示。应用锁不能约束外部编辑器，不承诺无条件的跨程序原子比较替换。

冲突副本放在 `data/reports/conflicts/YYYY-MM-DD.<run_id>.md`，不自动升为主文件。用户处理冲突后执行修复或普通重跑。主文件发布成功前不推进交付检查点。

`partial` 报告发布成功后返回 0，并保留缺口，不无限自动重跑。`no_changes` 同样必须落盘后返回 0。预检和预览成功也可返回 0，但不推进发布检查点；查询已成功且完整的报告可返回跳过成功。不可用、预算耗尽、锁等待超时、输出冲突等返回 1，用户取消返回 130。任务重启后先检查可恢复性和剩余额度，不盲目重复生成。

| 公司模型别名或接口能力变化 | 固定网关与模型配置，变更后重新做合成能力检查和请求指纹隔离 |
| 网关响应已产生、结果尚未保存即中断 | 保留不确定调用和预算，明确无法保证外部计费恰好一次 |
| 新报告库被旧版本程序读取 | 回滚使用迁移前备份，保留新库副本与新产物，不把旧程序直接指向新数据 |
| 输出目录被用户编辑或占用 | 校验和、冲突副本和替换失败恢复共同保护；用户附注独立保存 |
| 真实目录超过时间或输入预算 | 有界停止或显式部分覆盖；新增预算必须在配置与验收中可见 |
| 调度状态成功但报告覆盖不足 | 分别检查任务退出码、发布状态和报告质量 |

实施失败时先停止该任务的新触发，保留运行证据。需要代码回退时核对已修改文件与用户改动，恢复匹配版本和报告库备份；扫描库不降级、不清空。恢复后重新做本地诊断及合成用例。

用户已明确批准“允许按照计划实施，如果需要授权默认通过”。当前执行范围覆盖 A1—A9，按依赖顺序推进；完成判定仍需要各阶段的实际验收证据：

- A1—A7：本地实现、合成用例、构建与离线验证。
- A8：公司网关联调与真实目录验收；有效凭据和已核实的模型能力仍是技术前提。
- A9：注册并启用每天自动运行，读取回任务定义并采集真实计划日证据。
- Git 提交、推送、合并、对外发送报告或删除原始数据均不由本计划自动授权。
