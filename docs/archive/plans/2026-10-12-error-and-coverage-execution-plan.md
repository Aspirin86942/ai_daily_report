## 2. 完成标准与统计口径

### 2.1 历史问题的用途

原方案记录 1,418 条逐日报来源，748 条有非空摘录；434 条空摘录中有 323 条摘录预算耗尽、111 条 PDF 已读窗口无字。230 条未安排解析中，226 条属于预算问题、4 条属于体积策略。16 次失败模型请求包含 14 次截断和 2 次网关 502。

这些数字用于选择回归场景和样本，不能直接承诺全部恢复。候选数或 PDF 名额已经实际耗尽时，改变分配仍会保留缺口。原文件当前版本也无法还原已覆盖的历史版本。

### 2.2 主状态与四层覆盖

统计单位固定为 `target_date + scope_id + source_id`。文件来源单独统计，`user_input` 单列。一个文件来源只具有一个主状态，缺口标签可以有多个。

| 字段或指标 | 定义 | 验收规则 |
| --- | --- | --- |
| `registered_count` | 扫描实际登记的唯一文件来源数 | 不代表整个业务目录的独立文件总数 |
| `usable_excerpt_count` | 成功解析、具备稳定内容哈希，且包含有效业务内容的来源数 | 空白、页眉占位和无正文提示不计入 |
| `not_parsed_count` | 尚未安排正文解析的来源数 | 预算、策略、运行截止等原因分别记录 |
| `parse_failed_count` | 解析或来源稳定性验证失败的来源数 | 超时保留子原因，主状态计一次 |
| `empty_excerpt_count` | 解析成功但没有有效摘录的来源数 | 区分预算耗尽、窗口无字和有效空文档 |
| `model_covered_count` | 有范围进入成功且通过校验的模型批次的来源数 | 计划装入、仅预约调用、失败和未知调用不能当作成功覆盖 |
| `presented_count` | 最终摘要或待核实条目实际引用的来源数 | 只证明引用关系；事实正确性另行核验 |

必须满足：

```text
registered_count
  = usable_excerpt_count
  + not_parsed_count
  + parse_failed_count
  + empty_excerpt_count
```

“已登记 → 可提取 → 已送模 → 已呈现”分别计算。报告头采用“成功批次覆盖”这一明确名称；网络发送尝试及未知发送结果另存审计。没有可靠来源字段的旧日报显示“未知”，不补零。

### 2.3 核心验收门槛

| 维度 | 必须达到的结果 |
| --- | --- |
| 口径 | 合成场景及授权样本逐日主状态核平；缺口标签去重后可回查主来源 |
| 摘录公平性 | 总预算能容纳全部有效来源首份内容时，预算造成的零摘录来源为 0；不足时遗漏来源与原因完整 |
| 模型首片覆盖 | 批数、字节和总预算能容纳首片时，有效来源首片成功覆盖率为 100%；不足时分母与遗漏完整 |
| 可追溯性 | 新生成报告的所有引用指向本次成功批次中的来源及真实读取范围；无法确定范围时明确未知 |
| 内容质量 | 合成夹具的关键金额、日期、单位和小计/合计语义均符合预期；真实样本无新增错误数字或无依据事实 |
| 恢复 | 全缓存场景 `transport.prepare`、`transport.send`、新增调用预约均为 0 |
| 边界 | 文件数、页行、字符、批数、尝试数、tokens（模型计量单位）、费用、截止时间均不突破明确上限 |
| 历史保护 | 候选失败、发布失败或检测到手工修改时，旧当前版本与其正文保留 |

零摘录率同时提供两个分母：全部登记来源，以及已经成功解析的来源。首片覆盖率的分母为有效摘录来源。关键事实检出率使用验收前固定的事实清单，不能在看到结果后删除遗漏项。无来源日期和不可用日期分别呈现，不参与除零计算。

### 3.2 预算的层级和建议新增配置

已从源码确认的默认边界如下；运行机器的实际值由 T0 导出脱敏有效配置后冻结。

| 层级 | 当前默认或文档记录 | 本计划处理 |
| --- | --- | --- |
| Rust daily 准入 | 96 个候选、80 个 PDF 分类页、8 个 PDF 正文提取名额 | 上限保持；区分预约与实际消耗 |
| Rust daily 截止 | 10,000 ms | 解析、补缺、哈希与收尾共用既有运行截止，补缺不重置计时 |
| 文档提取 | PDF 至多 5 页、Excel 每表至多 50 行、文本至多 6000 字符 | 页行范围由实际解析结果报告，采样仍受各自上限约束 |
| 摘录总量 | 文档记录 50,000 字符；原生读取 `parse.aggregate_max_chars` | 两轮分配共用一个总额 |
| 旧 Markdown context | 默认全局 500,000、单文件 100,000 字符 | 继续回归旧消费路径；本次只做有限预约回收 |
| 模型请求 | 16,000 UTF-8 字节/批、8 个来源块/批、8 批 | 首片和深化共用这些限制，计入元数据开销 |
| 模型调用 | 3 次/逻辑步骤、12 次/运行、30 次/北京时间自然日 | 成功、失败、未知、预览和重试都计入 |
| 输出额度 | 操作文档记录日常 8192 tokens/请求 | 不提升生产配置，实际值以脱敏有效配置为准 |
| 应用截止 | 900 秒；任务执行上限文档记录 20 分钟 | 网络、退避、采集重试检查同一剩余时间；真实任务配置在上线时读取核对 |

96 个候选与 10 秒属于一次原生 scanner run。现有来源不稳定恢复允许额外一次扫描；两次分别记录原生预算消耗，同时占用同一应用运行的 900 秒预算。补缺轮次发生在一次原生扫描内，不额外启动一个拥有全新配额的扫描。统计报告来源与实际解析工作量时保留这个层级区别。

以下为拟新增配置与建议值，不是已生效配置：

| 建议配置 | 推荐值 | 规则 |
| --- | ---: | --- |
| `scanner.coverage_allocation` | `fair_two_pass_v1` | 新算法有独立版本，可显式选择旧策略回退 |
| `scanner.source_excerpt_min_chars` | 512 | 首轮目标；更短的有效文档可全文纳入；完整内容单元不足空间时明确遗漏 |
| `scanner.source_excerpt_quantum_chars` | 512 | 第二轮每次增加的目标，不切断已识别表格行或句子 |
| `scanner.max_refill_rounds` | 2 | 值为 0 可关闭；每轮必须具有实际进展 |
| `scanner.csv_allowed_encodings` | 仅 UTF-8/BOM | GB18030 仅在显式加入允许列表后使用 |
| `scanner.pdf_probe_policy` | `bounded_page_sample_v1` | 后续页探测从现有单文件和全局页额内分配 |
| `model_requests.allocation_policy` | `source_first_slice_v1` | 来源首片优先，深化在第二轮 |
| `model_requests.max_strategy_changes` | 1 | 每个原始逻辑批次的截断策略最多变化一次 |
| 自动 OCR | 关闭 | 启用必须具有已批准引擎及页数、时长和输出上限 |

512 字符是分配目标，不能证明语义完整。格式化标题、列名、单位等开销计入预算；首份内容必须包含实际内容单元，不能仅以几个字符或标题计作成功覆盖。

当前模型主要使用字节和调用数约束，尚不能把它们称为已经实现的总 token 或金额账本。T3 将补充每运行、每日及历史作业的 token/费用预约。初始额度从实际有效的调用数、单请求输入保守估算和输出上限推导，不扩大当前可发送的最坏上界。字节、估算 tokens、真实 usage 和计费金额分别保存。

金额上限依据网关实际费率填写。费率、币种或既有未知费用没有核清时，真实验收保持阻断；本地测试使用确定费率的替身。未知 usage 占用保守预约，不释放成零。

### 3.3 指纹与恢复身份

指纹是用来判断两份输入是否相同的校验身份。至少纳入以下内容：

- 来源稳定身份、原文件哈希、摘录哈希、实际范围与抽样策略。
- 解析器及 worker build、编码允许列表、格式探测和缓存载荷版本。
- 准入、补缺、摘录和模型首片分配算法版本及其预算参数。
- 提示词、批次 schema（输出结构约束）、合并规则、模型及影响结果的请求参数。
- 截断策略版本及实际选定的请求修订。

初始输入指纹包含原始计划和完整策略版本；实际请求修订另有有效计划指纹，保存到最终发布证据。普通重跑复用原结果时沿用已选定的成功修订；模板或附注变化只重新渲染这份已完成结果，不按最初的大批次重发。

观察时间、耗时、缓存命中描述、随机 run ID 和运行通道状态不加入内容身份。来源、提示词、schema 或模型语义改变时拒绝错误复用。凭据缺失、transport 禁用和额度耗尽属于发送条件，不阻断已经验证成功响应的纯本地恢复。

冻结输入快照维持不可变。策略调整写入新的计划修订快照，通过父请求指纹关联。旧输入快照版本继续使用其原有批次校验契约；新小 schema 不用于追溯否定已经合法保存的旧响应。旧冻结内容只能按原语义恢复，不能重新解释为新策略证据。

## 4. 工作项与执行顺序

执行链：`T0 → T1 → T2 → T3 → T4 → T5 → T6 → T7 → T8 → T9 → T10 → T11 → T12`。这是同一候选版本的内部依赖顺序，核心工作全部完成后再进入真实验收；不在中途上线半套能力。

### T0. 固定基线、有效配置和对照夹具

**输入与修改范围：** 当前代码、原方案、已有测试及配置读取入口。增加脱敏配置导出与合成对照夹具；证据落在 `.artifacts/coverage-optimization/<run-id>/`。原始业务目录只在获准的真实验收中使用。

**执行：**

1. 核对分支、HEAD、工作区和 CPython 3.13.13；实施开始时重新检查，保留其他任务的改动。
2. 通过现有配置对象按允许字段导出最终合并值，记录环境覆盖是否生效；不转储配置文件或环境变量。路径使用根别名，网关记录批准的目标身份，凭据只记录存在性。
3. 固定“几个大文件靠前、多个小文件靠后”、超过来源配额、混合格式和关键事实在后排的合成语料。记录文件哈希、预期事实与范围。
4. 为现行算法保存同一语料下的摘录、计划、耗时和预算消耗。真实网关由替身代替；读取旧账本只能使用统计和脱敏字段。

**交付与验收：** 基线清单、有效配置快照、预期事实清单、当前算法对照数据；能够在相同配置与夹具下重现来源和计划身份。此步骤只固定证据，不调大生产预算。

7. 自动 OCR 若获准接入，仅处理明确选中的 PDF 页；其调用占用独立 OCR 额度及同一运行时间。保留原页定位，未核实的金额、日期、比例和名称进入待核实项。

**交付与验收：** 前页无字后页有字、纯图片、真实空白、损坏、加密、探测超时及 OCR 哈希不符均可区分；未知保持未知。主要回归：`test_pdf_classifier.py`、`test_document_parser_worker.py`、`test_evidence_daily_service.py`、Rust `classifier_contract`。

完整 DOCX/PPTX 主后端与 fallback 预算语义一致性作为本次受影响范围的回归要求。独立的全面解析器重构和自动 OCR 引擎采购不纳入核心交付。

### T10. 显式历史补覆盖、候选发布和追加事件

**主要文件：** `scripts/backfill_daily_reports.py`、`evidence_daily.py`、`report_run_store.py`、`publication.py`、`snapshots.py`、`docs/daily-report-operations.md`。

**拟新增命令语义：**

| 模式 | 行为 |
| --- | --- |
| `--repair-coverage --dates ... --gap-codes ... --dry-run` | 从既有元数据筛选日期与缺口，列出读取范围、调用/token/费用最坏上限；不调用模型、不发布 |
| 上述预检加 `--refresh-preflight` | 在明确批准的文件范围内执行本地采集，刷新预检；扫描索引可能更新，模型调用为 0 |
| `--repair-coverage --plan <manifest> --generate-candidates` | 校验冻结计划、文件范围与预算，生成候选 JSON、Markdown 和差异；旧日报继续为当前版本 |
| `--publish-candidates <manifest>` | 校验已批准候选和旧当前版本，使用已存正文发布；不扫描、不调用模型 |

以上参数为待实现接口，不是当前可执行命令。新模式与旧 `--only-failed` 互斥；没有选择日期、缺口或具名计划就拒绝执行。原命令保留已发布 `partial` 的行为不变。

**执行：**

1. 预检计划记录 job ID、日期、缺口码、批准的根/文件范围、现有 run ID 与正文哈希、来源内容身份、配置/算法版本及预算。既有预检不足时明确标记估算条件，不自动扫描整个历史窗口。
2. 为新作业创建独立目录，保留既有 183 天补录的 `state.json`、备份和额度。日常与历史具有各自作业预算，同时保留全应用自然日总限额。
3. 复用现有 `preview` 运行及快照机制持久化候选输入、JSON、Markdown 和差异。候选不改变 `daily_reports.current_run_id`；候选主体和范围绑定冻结指纹。作业恢复继续使用已登记的候选 run 与 generation；普通日常恢复不自动发布这些待审阅候选。
4. 历史作业预算按已登记的 run ID 统计，不直接把“起始 call_id 后的所有应用调用”当作该作业消耗。run ID 关联必须在首次预约调用前可靠保存，恢复时不能重建新额度。
5. `state.json` 保持当前进度视图，新增 `events.jsonl` 追加事件：唯一事件 ID、job/run ID、日期、阶段、动作、前后质量及指标、错误码、调用增量、时间、旧/候选/发布版本。
6. 在同一作业锁中追加并刷盘事件，再原子更新视图；崩溃后用既有账本与事件重新核对。重复恢复不重复记同一事件；尾部不完整事件保留诊断并进行有界恢复，不能清空历史。
7. 候选验收检查关键事实、真实覆盖和预算后，发布已有候选正文。复用 `stage_report → publish → mark_published`，创建与候选绑定的发布运行，避免再次生成模型请求。
8. 发布前校验旧当前 run ID 和实际主文件哈希。旧版本变化、手工修改或候选身份不符时停止并保留冲突候选；文件核验通过后才切换当前数据库记录。
9. 失败保留旧版本、成功响应和调用审计。相同计划恢复复用相容批次；算法或文件改变时创建新的具名计划，旧消耗仍保留。

**交付与验收：** `partial` 日期可显式选中；预检零模型调用；候选失败不改变主文件；候选发布零新模型调用；恢复不重复计费；事件、状态与账本可核平。回归 `test_backfill.py`、`test_evidence_daily_service.py`、`test_report_recovery.py`。

## 6. 样本对照与上线门槛

每个日期输出一行对照记录，并可定位到来源级明细：

```text
日期 / 输入哈希 / 有效配置 / 算法版本
登记来源与四类主状态
预算导致的零摘录数与比例

保守费用预约、实际费用、未知费用状态
基线 run ID、候选 run ID、旧/候选正文哈希
```

上线必须同时满足：

1. 全部硬性边界用例通过，真实样本没有超出批准的调用、token、费用或截止预算。
2. 具备可分配剩余容量的压力样本，预算造成的零摘录数下降且首片覆盖提高；其他样本不因新分配出现无说明的类别遗漏。
3. 真实样本关键事实检出不低于对应基线，错误数字与无依据事实为 0。覆盖字符更多不能抵消关键内容变差。
4. 来源、页行、模型成功输入和最终引用可追溯；OCR 未核实和未知范围准确披露。
5. 新旧缓存、旧快照、候选发布和用户修改保护通过；生产运行使用已核验的完整代码包及配置。

真实样本耗时可能增加，必须给出增量和仍能在规定窗口结束的证据。若耗时或内容质量未达门槛，候选保持未发布，修复已查明原因后重新验证受影响部分。不得用降低质量标记或扩大总预算掩盖失败。
