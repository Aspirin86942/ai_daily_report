版本 v1.0

日期 2026 年 10 月 12 日

## 1 结论与建议顺序

建议保留现有 Rust 扫描、Python 编排和 Markdown 发布流程，围绕“有限预算内，多覆盖有价值的来源，并明确展示遗漏”做小步优化。现阶段最值得先改的是摘录预算分配和未解析文件的有界补缺，其次才是模型截断与少量解析兼容问题。

183 天日报已经交付，不能据此判定内容完整。附件显示，模型失败请求只有 16 次，但 1,418 条来源登记记录中有 670 条没有可用非空摘录；这是比单纯降低报错率更直接的内容质量问题。也不能把所有缺口都当成程序错误：限页、限行、限时和体积策略有其保护作用，应改进分配和说明，而非取消限制。

推荐顺序：

1. 先统一覆盖口径，修复全缓存恢复仍依赖网关的边界问题，保留现有安全限制。
2. 优先改善 323 条“解析成功但摘录预算耗尽”的来源，增加每来源首轮最低摘录和模型首轮覆盖。
3. 对 226 条预算类未解析记录增加有上限的补缺轮次；另 4 条体积策略拒绝单独处理。
4. 根据失败类型修 `.xls` 格式不符、文本编码等兼容问题；对 111 条 PDF 窗口无文字进行分诊，再决定是否采用有限 OCR。
5. 对模型截断采用可验证的小输出契约和有界策略切换；最后只挑少量历史日期对照验证，不重跑全部 183 天。

本稿是优化建议，尚未实施。未修改代码、业务文件、任务调度、历史日报或模型配置，也未执行真实业务样本扫描与付费模型调用。性能、覆盖改善和成本收益均需后续测试。

## 2 附件说明了什么

日报所属日期为 2026-04-12 至 2026-10-11，来源为上传的 `历史日报错误分析_2026-04-12_2026-10-11.xlsx`。模型失败、首轮恢复和扫描诊断的执行时间均在 2026-10-12，北京时间。因此，这是本次历史补录的统计，不是六个月连续生产运行的故障率，也不能按日报月份推断模型稳定性趋势。

230 条未解析进一步拆为：PDF 分类页预算 114 条、PDF 正文提取名额 27 条、候选文件预算 47 条、全局上下文预算 38 条、体积策略 4 条。前四类共 226 条，适合研究更公平的预算分配；“取消所有上限”不在建议之列。

典型例子是 9 月 22 日日报：登记 129 条来源，仅 12 条有非空摘录；55 条未解析，62 条空摘录。该日的 8 次模型调用没有失败，日报仍然部分覆盖。这说明模型成功率无法替代内容覆盖质量。来源：`183天明细!A169:M169`。

### 2.2 缺口标签不能当成独立文件相加

`文件内容缺口` 有 1,466 行缺口记录：1,465 条带来源的标签和 1 条旧版无来源诊断。按“日报日期 + 来源 ID”去重后有 1,191 个带缺口的来源记录。这不代表整个扫描目录只有 1,191 个文件。

例如，`EXCERPT_BOUNDED` 为 457 条、`PARSE_BOUNDED` 为 680 条，两者重叠 223 条；6 条 `PARSER_FAILED` 全部也有 `SOURCE_UNAVAILABLE`。`MODEL_INPUT_BOUNDED` 为 72 条，其中 35 条同时有解析范围受限。日报、诊断、缺口标签、来源登记和模型请求必须保留各自统计单位。

上述 72 条模型输入受限记录中，53 条虽然有摘录但 `model_chars=0`，另 19 条只发送一部分。这里的模型字符是进入已成功批次的切片长度，不代表模型已经正确理解或在最终摘要中引用；也不能把这个子集的比例扩展为全库比例。

### 2.3 截断不宜直接归因于输入太长

14 次截断的输入为 3,914 至 6,166 tokens，输出上限均为 8,192。记录中推理 tokens 占输出至少 90.72%，其中 10 次与全部输出 tokens 相等。主要可见症状是输出额度被推理占用，不能据此简单认定“JSON 太长”或“输入超过上下文”。

应先核实公司网关的实际模型、输出额度含义及支持的推理参数，再比较缩批、缩短结果契约或受控输出额度的效果。不要未经确认向网关发送猜测的“关闭思考”参数，也不要直接把全局输出上限长期拉到 32,768。

## 3 最新代码中应保留的能力和需要补齐的部分

### 3.1 已有能力不重做

- 最新代码已具备目标日报日与时区窗口、Windows 每日 09 点任务支持、手工修改保护、`repair-output`、持久化调用记录及补录预算控制。本方案是在这些基础上补覆盖和质量；代码具备能力不等于当前机器的调度已经完成长期验证。
- 扫描缓存行顺序导致的比较失败已通过构造时排序和回归用例修复，不能继续列为当前待修故障。
- 已有模型调用记录、响应快照、截断检测、验证失败次数限制和已成功批次复用。不要另建一套模型调用平台或日志系统。
- 已有本地 OCR 结果导入旁路，用于补录时核对文件哈希后引入预先生成的文字，并标记需要核实。它不是每日服务自动执行 OCR，也不是“完全没有 OCR”。
- 已有解析、候选、页面、字符和运行时限。它们是稳定性与成本保护，需要保留。

### 3.2 静态核查发现的当前问题

| 位置 | 当前行为 | 建议 |
| --- | --- | --- |
| `sources.rs` | 按相对路径依次消耗总摘录预算，后排可能得到零字 | 首轮保底，再用剩余额度轮转深化 |
| `model_plan.py` | 按来源 ID 顺序分片填批，达到最大批数后没有每来源首片兜底 | 先让更多来源进入首轮，遗漏必须可计数 |
| `admission.rs` | 固定候选和页数配额，预算耗尽不继续回填 | 保留确定性，增加有截止时间的有限补缺轮次 |
| `model_calls.py` | 截断可重试相同请求和相同输出上限 | 按错误分类；截断后产生更小的新计划并记录变化 |
| 批次结果契约 | 提示词要求最多 6 条摘要、3 条待核实，但通用 schema 可容纳远大于此的输出 | 批次单设严格小 schema，最终合并使用自己的上限 |
| 并发恢复 | 多 worker 多批时，即使全部成功结果已存盘，仍先准备 transport | 先判断哪些批次真的要发送，纯恢复不检查网关额度与凭据 |
| 补录状态 | `state.json` 保存最终快照，会替换同日期上次状态 | 保留快照，补充追加式补录事件，复用已有运行和调用审计 |

还有一个操作语义必须明确：现有补录脚本把已发布的 `partial` 日报视为已完成并保留；`--only-failed` 不会选择这些日报。`repair-output` 只是重建已存正文，不重新扫描或补充模型输入。后续若要改善历史内容，必须新增显式的“选择缺口后重新生成”入口，不能让用户反复运行旧命令却期待覆盖提升。

## 4 先建立可追溯的覆盖说明

在现有来源、计划和日报元数据上增加字段，不先引入新数据库、任务平台或服务。

每个来源至少记录：日期、来源 ID、文件内容指纹、解析器版本、实际策略、主状态、主缺口原因、次级标签、读取页行范围、摘录字符数、送模字符数、所处批次，以及是否使用需要核实的 OCR 文字。对失败保留脱敏错误和阶段；不把完整业务路径、正文或密钥写入通用日志。

应区分以下四层：

1. 已登记：本次扫描范围内发现并登记的来源。
2. 可提取：获得非空文字或结构化内容，但可能仅覆盖部分页行。
3. 已送模：实际请求中包含哪些来源和范围。
4. 已呈现：日报哪些结论引用了哪些来源，是否出现没有依据的新数字或事实。

“没有错误”“解析返回 success”“已经发给模型”“摘要引用过一次”都不是全量覆盖的同义词。若扫描本身受目录、候选数或时限限制，也要把这一层边界写出来。

报告头建议增加一段机器生成的覆盖摘要，例如：登记 N 条，非空摘录 A 条，已送模 B 条，未安排解析 C 条，解析失败 D 条，空摘录 E 条；主要缺口是什么。本段由结构化元数据生成，不交给模型估算。没有可靠字段的旧日报显示“未知”，不要补成零。

继续保留 `partial`。只要受限页行、OCR 未核实或来源未送模等事实仍存在，就不能为了好看把状态改成完整。主要验收指标应是零摘录率、首片送模覆盖率、关键内容检出率及可追溯率，而不是 `partial` 数字归零。

## 5 扫描和摘录预算怎样改

### 5.1 用两轮分配改善后排来源被遗漏

第一轮按稳定、可解释的顺序为可解析来源分配少量有效内容；第二轮在剩余预算中轮转补深，兼顾文件类型与用户指定的重要目录。保留稳定排序保证可复现，但不要让路径或哈希顺序单独决定谁能获得全部内容。

最低摘录是“尽量覆盖”的目标，不是无条件承诺。若最低额乘来源数已超过总额，应显式选取有限集合，记录未覆盖原因；不能突破总预算，或把每份文件压成没有语义价值的几字标题后声称已覆盖。

PDF 优先保留页码和有文字的段落；表格优先保留工作表名称、表头、单位、关键行及合计信息；长文本按段落与章节取样。不要只截前 N 字导致目录、封面或固定页眉占满。任何取样均须记录实际范围，避免把局部合计误写成全表合计。

### 5.2 对未安排解析做有上限的补缺

先识别原因，再选择动作：

- 页数或候选预算：在本次剩余时限和总预算内，增加有限轮次回填；实际消耗少于预约额时可返还额度，但只返还确实未消耗部分。
- 全局上下文预算：优先缩小单来源占用和轮转分配，而不是只增大上限。
- 体积策略：保留拒绝或仅元数据状态，单独请求是否需要对特定文件扩大范围。
- 超时或临时不可读：按明确次数重试；持续不可读记为缺口。

默认不建设永久积压队列。若日后确有跨日补充需求，队列必须有限长、有过期时间、去重键和最大尝试次数，历史材料要保留原业务日期，不能无标记混入当天日报。每日任务到截止时间即结束补缺并发布真实的部分覆盖结果。

仓库 daily 模式每次扫描的默认值包含候选数 96、PDF 分类总页额 80、PDF 正文提取名额 8，以及扫描器总 deadline 10 秒。这里的 8 是提取名额，不是单 PDF 页数。应用侧另有 900 秒限制。这些是不同层级的默认值，不代表运行机当前配置。实施前先导出脱敏的有效配置，再决定调哪一层；不能只把 900 秒加大并期待扫描器多读内容。

中期还应梳理重复预算：日报消费结构化 sources，但 Rust 准入仍使用旧 Markdown context 预算，并同时构建两种输出。因此 38 条 `global_context` 限额不只是模型输入限制。先做有限补缺，再考虑 evidence 专用轻量准入或统一采集、摘录、发送预算；不要再叠加第四套无关截断。改动旧 context 路径时必须回归周报、月报。

## 6 解析器按失败类型修

### 6.1 优先修小而确定的兼容问题

`.xls` 扩展名但实际为 XLSX 的文件，当前路由进入 legacy 分支后可能把自动识别出的 openpyxl 对象当成 xlrd 对象使用。建议优先在 legacy adapter 内做受控格式探测与 engine 分支，保留原扩展名及识别格式；不简单改写严格契约中的文件类型，不要求用户批量改名，也不更改原始文件。增加“扩展名与真实格式不一致”告警和合成回归样本。

CSV 目前严格 UTF-8。若业务确有 GB18030，应作为显式允许的有限编码策略：UTF-8/BOM 优先，失败后仅尝试配置允许的严格编码，记录最终 encoding 和告警。截取头尾时处理多字节边界，编码配置与版本纳入解析指纹；JSON 不随之放宽。禁止用 `ignore` 或替换字符掩盖解码失败，因为财务名称和金额附近文本可能被静默改变。

加密、损坏、文件占用和类型不符应使用不同错误码。重试只能用于可能恢复的原因；加密文件不自动尝试密码，损坏文件不无限重试。

附件中的六条解析失败有文件探测归因，但本次没有打开这六个原始业务文件验证，不能把附件描述写成已复现根因。有效但没有正文的 DOCX 与 0 字节、损坏 DOCX 也应区分；现有解析器可能返回无正文占位符，不能把占位符当作业务正文送模。

诊断细化使用安全的枚举子原因。现有代码有意隐藏底层异常以避免单元格内容泄露，应保留这条防线，不把完整异常或文件正文重新写入日志。DOCX/PPTX 主后端与 fallback 的页段、表格、幻灯片预算语义一致性列为后续加固，先不放宽超时掩盖问题。

### 6.2 111 条 PDF 窗口无字应先分诊

“当前读取范围内无文字”可能意味着文字在后续页、图片型页面、保护或抽取兼容问题，也可能确实只有图像；现有统计不能证明这 111 条全部是扫描件。

建议先做有页数上限的探测：检查现有文本层、有限后续页和解析诊断。只有确定需要图像识别、且值得处理的来源才进入可选 OCR。复用已有 OCR 文字与文件哈希验证方式，把旁路封装成有限页数、有限时长、可关闭的本地 worker。先不让 OCR 成为每日全目录默认动作。

OCR 输出保留 `text_unverified` 与页码，不自动升级为已核实事实。金额、日期、比例、名称等关键字段若进入正式摘要，应有可回查的原页位置；未核对部分进入“待核实”。任何云端 OCR 或新增外发模型都需另外确认数据范围与接收方。

## 7 模型输入和输出怎样改

### 7.1 先覆盖来源首片再增加深度

在固定最大批数和总 tokens 内，第一轮优先装入更多来源的第一份有效片段，第二轮才增加长来源的后续片段。批次要包含来源 ID 和页行范围；未发送部分沿用 `MODEL_INPUT_BOUNDED` 等真实状态。

不要一文件一调用，也不要先逐文件总结再无限合并。维持有限数量的批次和现有合并方式，暂不新增模型汇总层。全部模型请求，包括重试，都计入同一运行的调用和费用上限。

### 7.2 按错误原因重试

| 情况 | 建议动作 | 停止条件 |
| --- | --- | --- |
| 网关 502、限流等暂时问题 | 有界退避；存在有效 `Retry-After` 时遵守 | 达到尝试数、运行截止或成本上限 |
| 明确输出截断 | 不重复同样的大请求；缩小批次或减少结果项目，生成新计划版本 | 新策略仍失败，或无足够预算 |
| JSON/schema 不满足 | 严格校验；必要时一次有界修复或重生成 | 禁止把未闭合或半截 JSON 当成完整成功 |
| 凭据或参数不合法 | 明确阻断，保留已完成成果 | 不盲目循环重试 |

对批次结果单设小 schema，落实提示词的短输出要求，例如当前约定的摘要最多 6 条、待核实最多 3 条，并限制单条长度。最终报告如需更多项目另设边界，避免把通用大 schema 的容量当作批次输出目标。小 schema 能约束可见输出，但不能单独解决内部推理用尽额度。

记录 `finish_reason`、输入与输出 usage、推理 tokens（网关有返回时）、批次来源数、实际请求参数、重试原因和策略变化。缺失用量应标记未知，不计为零费用。复用已有调用记录与快照，并避免把完整敏感正文放入面向日常查看的错误日志。

### 7.3 缓存恢复必须可离线

先读取已保存的成功响应，确定待发送批次，再准备 transport。若所有批次均可复用，即使模型被禁用、凭据暂不可用或补录额度已用尽，也应能从本地证据继续合并和发布。

复用前仍须检查输入指纹、解析器及提示词/schema/模型配置版本；采集和模型计划算法改变也要版本化。来源或策略变化后不能把旧摘要当成新证据；指纹兼容的成功批次尽量复用，版本一致的纯输出恢复则不应重新调用模型。

## 8 实施边界与成本控制

### 8.1 保持现有架构

改动集中在现有 admission、source 构造、model plan、model call、解析分流和补录入口。覆盖元数据跟随现有产物保存，沿用现有原子发布和运行记录机制。不新增消息队列、向量数据库、多服务编排或常驻模型进程。

每次运行保存脱敏的有效配置、代码版本、输入指纹、计划版本和最终质量。保留 `state.json` 为当前进度视图，额外追加补录事件：日期、job/run ID、阶段、动作、前后质量、错误码、调用增量、时间和替换版本。这样既不丢历史，也不用把现有日志系统推倒重来。

### 8.2 在开始前计算能否承担

日常与历史修复使用独立预算，至少同时约束：文件数、读取页行数、摘录总字符、模型输入和输出 tokens、请求总次数、OCR 页数/时长、总运行截止时间。任一上限触发都应停止扩展工作并记录缺口。

首轮试验建议不提高现有生产总调用与总 token 上限，只改变分配方式；需要增加时以配置变更单独比较。金额上限在核实实际网关费率后设置为明确的每运行与每日限额，重试包含在内。费率或已耗费用未知时，不以零成本继续无限调用。

历史修复先 dry-run：列出日期、缺口类别、计划读取范围、最大调用数、最大输入/输出 tokens 和预计费用上限，再授权执行。预估不是结算，最终以网关实际 usage 和计费记录为准。

## 9 分阶段落地与验收

### 阶段一 口径和安全性小修

交付：覆盖摘要、主缺口分类、有效配置快照、并发纯缓存恢复修复、批次短 schema、追加式补录事件。

验收：统计主状态可逐日核平；未知字段不补零；成功调用可复用；全缓存恢复时 transport 调用为零；错误分类和成本统计没有重复计数。此阶段不改变真实文件的扫描范围。

### 阶段二 覆盖优先分配和解析兼容

交付：摘录两轮分配、模型首片优先、有限预算回填、格式探测和受控编码支持；PDF 分诊与 OCR 开关暂以合成数据验证。

验收：同样总预算下，预算允许时每个有效来源至少获得一段有意义的摘录；不能保证时准确列出遗漏。来源顺序改变不应导致一整类文件长期零覆盖。所有上限、取消信号和截止时间有效。

### 阶段三 少量授权样本对照

先由用户确认允许读取的日期和文件范围。建议从典型高负载日、PDF 集中日、表格集中日及曾截断日中选少量日期，例如 3 至 5 天；只作为抽样设计，不自动执行。优先复用已有基线快照、响应和统计，只在缺少必要指标或条件不可比时重跑基线，再运行候选版本，全部受真实模型调用和费用上限约束。

比较内容：零摘录来源数、首片送模覆盖率、关键事实检出、错误数字和无依据结论、耗时及成本。不能用单纯字符更多或 `partial` 更少证明质量提高。若覆盖提升但关键事实更差，或预算、耗时超限，不进入生产。

### 阶段四 日常上线与可选历史补覆盖

通过验收后才合入生产配置。保持 Windows 每日 09 点工作流；先核对 Windows 本机时区、触发条件和实际有效配置。“09 点启动”和“09 点前拿到日报”是不同要求，若需要后者再讨论调度时间，不擅自提前或新增任务。

至少连续观察三个真实日常触发窗口，核查确有运行、仅一个实例、按设定上限结束、产物和覆盖说明对应本次运行。仓库已有运行记录不能替代当前机器的真实调度验收。

历史补覆盖使用新的显式入口，按日期和缺口码选择；现有已发布版本保留，候选版本通过内容与覆盖检查后再替换，并记录前后差异。默认不全量重跑 183 天。失败时保留旧版本，恢复代码和配置后可继续日常运行。

### 必须具备的自动化测试

| 测试场景 | 验收标准 |
| --- | --- |
| 多个大文件靠前，小文件靠后 | 不再因顺序无说明地把后排来源清空；不足时准确列缺口 |
| 页额、文件额、总额、deadline 分别耗尽 | 原因准确、有限结束、绝不突破上限 |
| 正文在 PDF 后续页、纯图片 PDF、损坏或加密 PDF | 分型正确；有限探测；不全部归为扫描件 |
| XLSX 内容使用 `.xls` 扩展名、GB18030 CSV、损坏表格 | 路由和编码可回溯；没有静默丢字 |
| 关键金额在后排页行，合计与局部小计并存 | 摘要能标明取样范围，不把局部内容误称全部 |
| 模拟 502、截断、半截 JSON、usage 缺失 | 有界重试；策略变化有记录；费用未知不视为零 |
| workers=3、至少两批、成功响应落盘后发布前中断 | 禁用 transport 仍可完成纯本地恢复，零新请求 |
| partial 日报选择性重生成失败 | 旧发布版本不丢失，历史和调用记录保留 |

所有这些先用合成数据和假模型完成。真实业务文件与实际网关只用于用户授权的有限验收，不把测试脚本指向整个业务目录。
