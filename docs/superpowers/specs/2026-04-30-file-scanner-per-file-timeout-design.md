# FileScanner 单文件解析超时设计

## 1. 目标

本次设计要解决的问题很具体：

- 周报、月报在 `--source scan` 时会真实读取并解析文件内容，不是只扫文件名。
- 日报同样依赖 `FileScanner`，因此同一类卡顿风险也存在于日报扫描。
- 当前限制只有行数、页数、字符数和全局字符上限，都是“内容预算”，不是“时间预算”。
- 一旦某个 PDF、Excel、PPTX、DOCX 或异常文本文件解析很慢，当前实现没有办法真正中断它，只能继续等待，容易浪费大量时间。

本次设计目标如下：

1. 为 `FileScanner` 的所有扫描场景增加“单文件解析超时”能力，包括日报、周报、月报。
2. 超时必须是真正可中断，而不是只在主线程报超时但底层解析继续运行。
3. 单个文件超时后，默认跳过该文件，记录错误，整次扫描继续。
4. 默认超时值为 `30s`，并允许按文件扩展名覆盖。
5. 不引入“整次扫描总超时”，本次只处理单文件超时。

## 2. 已确认边界

以下边界已由用户确认，本次设计必须严格遵守：

- 超时能力统一作用于 `FileScanner`，不区分 `scan_today_files()` 与 `scan_files()`。
- 单个文件超时后的默认行为是“跳过并继续”，不是中止整次扫描。
- 默认超时值是 `30s`。
- 允许按文件类型覆盖超时值。
- 本次不增加整次扫描的总时长上限。

本次不做的事情：

- 不修改 CLI 参数。
- 不改变 `main.py` 的调用接口。
- 不改变 `ScanResult` / `FileContext` 的结构。
- 不顺带重做扫描器的目录遍历策略、文件筛选策略或内容截断策略。

## 3. 当前实现判断

当前扫描流程位于 `src/services/file_scanner.py`，关键事实如下：

- `scan_files()` 先通过 `os.walk()` 全量遍历工作目录，筛出日期范围内的文件。
- 匹配到的文件会被一次性提交给 `ThreadPoolExecutor`。
- 每个任务执行 `_extract_content()`，根据扩展名进入 `_parse_excel()`、`_parse_pdf()`、`_parse_pptx()`、`_parse_text()`、`_parse_docx()`。
- 内容截断通过 `truncate_text()` 在解析完成后执行。
- `total_max_chars` 只是在结果汇总阶段把后续内容替换成“已达上限，内容省略”，不能阻止已经提交出去的解析任务继续跑。

这带来两个直接问题：

### 3.1 线程超时不能解决“真正中断”

如果继续沿用 `ThreadPoolExecutor`，再额外套 `future.result(timeout=30)`，主线程虽然可以尽快返回，但底层线程里的 PDF/Office 解析通常不会被真正取消。也就是说，超时提示可以更早出现，但 CPU、IO 和等待时间未必真的省下来。

### 3.2 当前很多限制发生在“读完之后”

- 文本文件是直接 `read_text()` 整体读入。
- DOCX、PPTX 会整体解析文档结构。
- Excel 是先读取工作表，再做 `head(max_rows)`。
- PDF 是打开文档后逐页提取文本。

因此，现有的行数、页数、字符数限制，无法覆盖“文件本身很慢”或“底层库卡住”的风险。

## 4. 方案选择

本次设计比较过三类方案：

### 4.1 方案 A：在线程 Future 上加 timeout

优点：

- 改动小。
- 基本不影响现有结构。

缺点：

- 不能真正终止底层解析。
- 对“某个文件卡住导致总时长被拖长”的问题改善有限。

结论：不采用。

### 4.2 方案 B：每个文件放到独立子进程，父进程按超时回收

优点：

- 可以真正中断单文件解析。
- 某个文件卡住时，损失被限定在该文件自己的超时窗口内。
- 失败语义清楚，最符合“不要继续浪费时间”的目标。

缺点：

- 每个文件会有进程启动和 IPC 开销。
- Windows 下必须显式考虑 `spawn` 模式和可 pickle 的 worker 边界。

结论：采用。

### 4.3 方案 C：调用外部 helper 脚本作为子进程

优点：

- 同样可以真正中断。
- 进程隔离更彻底。

缺点：

- 额外引入命令行协议、序列化和脚本维护成本。
- 对当前仓库来说复杂度偏高。

结论：不采用。

## 5. 设计方案

### 5.1 配置设计

在 `[scanner]` 下新增两个配置项：

```toml
[scanner]
file_timeout_seconds = 30
file_timeout_by_extension = {}
```

如需按扩展名覆盖，可显式配置，例如：

```toml
[scanner]
file_timeout_seconds = 30
file_timeout_by_extension = { ".pdf" = 45, ".xlsx" = 60 }
```

规则如下：

- `file_timeout_seconds` 是统一默认值，单位为秒。
- `file_timeout_by_extension` 是按扩展名覆盖的映射，键统一按小写扩展名处理。
- 若某扩展名存在覆盖值，则优先使用覆盖值。
- 若不存在覆盖值，则回退到 `file_timeout_seconds`。
- 若配置缺失，则默认回退到 `30`。

配置加载层需要同步更新 `Config.scanner_config`，把这两个字段暴露给 `FileScanner`。

之所以把“默认值 + 按扩展名覆盖”同时保留，是因为：

- 大多数团队先只需要一个全局默认值。
- PDF、Excel 这类文件的解析耗时分布通常明显长于文本文件，后续按类型微调是合理需求。
- 这样可以在不改代码的前提下做运行期调优。

### 5.2 执行模型

外层仍然保留当前的 `ThreadPoolExecutor(max_workers=...)`，但线程不再直接做文件解析，而是只负责“监督一个子进程完成单文件解析”。

执行链路调整为：

1. `scan_files()` 仍然负责筛文件、控制并发、聚合结果。
2. 外层线程池中的每个任务改为调用一个新的私有包装方法，例如 `_extract_content_with_timeout()`。
3. `_extract_content_with_timeout()` 为当前文件创建一个独立子进程。
4. 子进程只负责这个文件的真实解析，并把 `FileContext` 结果通过 IPC 返回给父进程。
5. 父进程使用 `join(timeout_seconds)` 等待。
6. 若超时仍未退出，父进程 `terminate()` 子进程并回收句柄，然后构造一个带超时错误的 `FileContext` 返回。
7. 若子进程按时结束，则读取其返回结果并继续当前流程。

保留外层线程池的原因不是为了叠加复杂度，而是为了尽量保持当前扫描器的吞吐和调用结构：

- `max_workers` 的语义不需要变化。
- 多文件并发能力仍然保留。
- 改动集中在扫描器内部，不会扩散到 CLI 和上层服务。

### 5.3 子进程 Worker 边界

Windows 默认采用 `spawn`，因此子进程入口必须是模块级可 pickle 的函数，不能依赖闭包或不可序列化对象。

因此建议把单文件解析拆成两层：

1. 保留一个“纯解析实现”，例如 `_extract_content_direct(file_path, limits)`。
2. 增加一个模块级 worker 函数，例如 `_extract_content_worker(file_path_str, limits, result_queue)`。

worker 的职责：

- 接收字符串路径和简单字典参数。
- 在子进程内调用纯解析实现。
- 把最终 `FileContext` 的可序列化表示写入队列或管道。
- 若子进程内抛异常，捕获后同样返回失败结果，而不是让父进程只拿到一个空退出。

这里刻意不把整个 `FileScanner` 实例直接传给子进程，原因是：

- 减少 pickle 风险。
- 降低配置对象、logger、Path 实例等边界复杂度。
- 让子进程协议保持简单，便于后续测试和排障。

### 5.4 超时判定与回收

超时处理需要尽量硬且清楚：

1. 父进程启动子进程。
2. 调用 `join(timeout_seconds)`。
3. 若超时后进程仍存活，则记录 warning 日志。
4. 执行 `terminate()`，随后再次 `join()`，确保句柄被回收。
5. 返回失败 `FileContext`：

```text
file_path = 原文件路径
file_type = 原扩展名
content = ""
error = "timeout: file parse exceeded 30s"
```

这里的错误字符串建议保留稳定前缀 `timeout:`，原因是：

- 便于日志统计和后续检索。
- 不新增 `timeout_count` 字段也能从 `contexts` 中识别超时数量。

如果子进程已退出，但父进程没有从队列中拿到合法结果，则同样按错误处理，错误信息建议形如：

- `subprocess exited without result`
- `subprocess returned invalid payload`

这样可以区分“真正超时”和“子进程异常退出”。

### 5.5 超时值解析

`FileScanner` 内新增一个私有解析方法，例如 `_resolve_file_timeout(file_type: str) -> float`，规则如下：

1. 统一把扩展名转成小写。
2. 先查 `file_timeout_by_extension`。
3. 找不到时回退到 `file_timeout_seconds`。
4. 仍为空时回退到默认值 `30`。
5. 若配置值小于等于 `0`，视为非法配置，回退默认值并记录 warning。

这样做的原因是把配置容错收敛到一处，避免超时逻辑散落在多个调用点。

### 5.6 与现有统计和上下文拼装的兼容性

本次不修改 `ScanResult` 和 `FileContext` 结构，因此现有上层逻辑保持兼容：

- `success_count` / `error_count` 的统计口径不变。
- 超时文件仍记入 `contexts`，只是 `error` 非空、`content` 为空。
- `main.py` 中的 `build_file_context()` 无需改接口，超时文件会自然以“文件 + 错误信息”的形式进入提示词。
- `summary_mode` 仍然只负责内容预算，不负责时间预算。

这个兼容策略的意义是把改动范围压在扫描器内部，降低回归风险。

## 6. 可维护性与可观测性要求

本次设计优先级是：

1. Correctness
2. Maintainability
3. Observability

基于这个优先级，除了超时本身，日志也要补齐：

- 扫描开始时记录默认超时值与扩展名覆盖配置。
- 单文件超时时记录 `file_path`、`file_type`、`timeout_seconds`。
- 扫描结束时在汇总日志中补充超时数量。

之所以要单独记录超时数量，是因为“失败”并不等于“超时”：

- 有些失败来自文件损坏。
- 有些失败来自编码错误。
- 有些失败来自第三方库异常。

如果没有单独的超时观测，后续就无法判断新能力到底有没有在真实场景里拦住卡顿。

## 7. 测试设计

### 7.1 配置测试

需要补充对 `Config.scanner_config` 的测试，确认以下行为：

- 能正确读取 `file_timeout_seconds`
- 能正确读取 `file_timeout_by_extension`
- 缺省时能回退默认值

### 7.2 超时解析测试

需要补充对 `_resolve_file_timeout()` 的单元测试，覆盖：

- 默认值命中
- 扩展名覆盖命中
- 扩展名大小写归一化
- 非法配置回退

### 7.3 扫描器聚合行为测试

需要验证 `scan_files()` 在以下场景下的聚合行为：

- 成功解析文件时，`success_count` 正常累加
- 单文件超时时，`error_count` 增加，且该文件返回空内容和 `timeout:` 前缀错误
- 超时文件不会中断其他文件的处理
- `success_count + error_count == total_files` 仍然成立

### 7.4 子进程超时路径测试

为了让测试稳定，建议不要依赖“真实大文件刚好很慢”这种偶然条件，而是在扫描器内部预留一个可控的私有封装层，例如：

- `_extract_content_with_timeout()` 负责超时控制
- `_run_extract_subprocess()` 负责实际启动子进程

这样单元测试可以 monkeypatch `_run_extract_subprocess()` 或 `_extract_content_with_timeout()` 的私有依赖，稳定覆盖：

- 正常返回
- 超时返回
- 子进程异常退出

原因很直接：Windows 的 `spawn` 子进程对 monkeypatch 传播并不友好，若把测试建立在“真实子进程里 sleep 后超时”上，维护成本会明显变高。

必要时可以再增加一个轻量集成测试，专门验证真实子进程路径可运行；但集成测试不应承担所有行为分支覆盖责任。

## 8. 风险与控制

### 8.1 风险

- 进程创建开销会高于纯线程模型。
- Windows `spawn` 下若 worker 不是模块级函数，会直接失败。
- IPC 若处理不当，可能出现子进程已退出但结果未正确回传的边界问题。
- 如果资源回收不完整，可能留下僵尸进程或句柄泄漏。

### 8.2 控制措施

- 保留外层 `max_workers`，避免无限制地同时拉起子进程。
- worker 必须设计为模块级函数，参数只传简单可序列化数据。
- 父进程对超时路径必须执行“判活 -> terminate -> join -> 返回错误结果”的固定顺序。
- 队列/管道读取失败时返回明确错误，不允许静默失败。
- 通过测试覆盖正常、超时、异常退出三条主路径。

## 9. 验收标准

本次设计对应的实现完成后，应满足以下标准：

1. `FileScanner` 的所有扫描场景都具备单文件超时能力。
2. 默认超时值为 `30s`，并支持按扩展名覆盖。
3. 单个文件解析超时后，扫描继续执行，不中断整次任务。
4. 超时文件会进入 `contexts`，其 `error` 可明确识别为超时。
5. 现有 CLI 和报告生成入口不需要修改调用方式。
6. 测试能够覆盖默认值、扩展名覆盖、超时聚合和异常退出等主要分支。

## 10. 非目标

以下内容明确不在本次范围内：

- 整次扫描总时长限制
- 扫描文件数量上限
- 文件大小上限
- 目录遍历优化
- 重新设计 `ScanResult` 模型
- 重新设计周报/月报 `file_context` 的组织方式
