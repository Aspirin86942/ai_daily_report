# 自动运行可靠性收敛设计

日期：2026-10-19。依据：用户已批准宏观建议后要求执行；本轮落实可靠性前两批，主代理连续执行、独立最终审查。报告阅读版与事项合并另行处理。

## 目标与边界

让采集、延期解析、晨间日报和健康通知形成可核对的闭环，避免命令退出成功掩盖材料未完成。保留 Rust + SQLite + Windows 计划任务，复用现有解析队列、进程隔离、发布及冻结恢复。

- 自动源文件采集仍为上海时间工作日 09、11、13、15、17、18 点；夜间、周末及登录补触发继续受窗口约束。
- 新的自动补解析也只在相同工作日窗口启动，只读取已归档原件，不发现或复制源目录文件，不调用模型。
- 内存总预算 3072 MiB、系统预留至少 2048 MiB、父进程 512 MiB、单 Worker 512 MiB和现有提取范围保持。OCR 关闭。
- 模型、提示词、单次请求限制、累计预算开关、全文覆盖、原件、旧包、历史缺口、失败账本和用户其他修改保持。
- 本轮允许显式手动补处理现有 153 项积压；不增加自动夜间采集，不手动生成生产日报或发送模型自检请求。
- 不提交或推送 Git，不删除旧材料。部署保存配置、任务 XML、数据库一致快照和源码差异。

## 一、归档补解析

新增 `archive drain [--scheduled] [--target-date YYYY-MM-DD] [--max-seconds N]`，默认最多 120 秒，允许 1–1200 秒。显式人工调用不受自动启动窗口限制；scheduled 在资源预算、锁和归档写入前检查窗口。

复用 `parse::drain`，以可选目标日的窗口末尾筛选已观察版本；同一内容只解析一次，保留原观察日期。无目标日时处理全部当前 profile 队列。注册缺少关联的现有版本，恢复被中断的解析，沿用确定性失败/瞬时失败三次重试策略。

运行共用归档单实例锁；自动运行遇到锁占用返回 `skipped/archive_busy`，不伪造完成。失败、延期、处理量、剩余量、耗时和原因均记账。

为保持 archive schema v1 及已有 `gaps/file_metrics` 外键，复用 `collections` 作为归档处理运行账本：补解析记录 `metrics.operation=parse`，状态严格使用 `parse_running/parse_complete/parse_partial/parse_failed/parse_interrupted`。这些状态不属于采集完成状态；连续性查询仅承认原有 complete/partial，普通采集查前次时间时排除 parse 记录。stats 将补解析明确分列为 parse_runs。历史采集状态不因后续补解析被改写。

增加 `AI Daily Report Parse` 计划任务，使用独立采集配置；每半小时检查一次，从窗口起点后 5 分钟开始，正式窗口为 09:05、09:35…17:35，并补上 18:00。零队列快速返回。任务不要求模型授权，自检及任务回读仍必须通过。

## 二、晨间材料就绪

只对新的、实际保存的 scheduled archive 日报，在模型冻结前检查目标日期的未完成解析；已发布报告和已有冻结恢复不重新处理输入。

先进行一次最多 120 秒的目标日补解析。源目录不可用不妨碍读取归档原件。若仍有队列或归档锁忙，在配置出报时间后的 30 分钟之前返回 `deferred/waiting_materials`、模型调用 0；不创建虚假的失败报告。09:30 兜底再次执行；达到截止时间后允许按明确的 `ARCHIVE_PARSE_PENDING` 缺口生成 partial 报告，保留迟到材料后续报告补充机制。

补解析后重新取得报告输入准备时间，使刚完成的解析能够进入本次冻结输入。目标日期及自然日窗口不改变。新采集的当日材料不会混入昨日报告。

## 三、结构化状态

保留日志已有字段以兼容消费者，增加 execution_status、material_status、publication_status、queued、errors、reason_codes，区分命令结束、材料就绪及报告发布。

- collect/parse 有错误或队列时顶层 status 为 partial，execution_status 为 succeeded；skipped 不算完成。
- daily 已发布与材料 partial 分别记录；等待材料为 deferred，不计成失败。
- health 的顶层 status 对齐 healthy/warning/unhealthy，execution_status 只表示检查本体执行。
- 真正的错误仍记录 failed、error_code、phase。

健康巡检继续只读检查数据库，队列证据增加最老观察时间、年龄和最近补解析原因。近 24 小时失败中，相同 scope/目标日已由更晚正式发布恢复的记录归入 resolved_failures，不再作为当前故障；原失败记录不删除。仍未恢复的失败和待续运行继续报警。

## 四、健康文件与通知

Rust 在 scheduled health 中先原子写入当天 UTF-8 健康 JSON，再记录调度事件；CLI 支持 `health --output <path>` 另存受控输出文件。临时文件与目标在同目录，刷新并原子替换，拒绝重定向路径。

PowerShell 通知脚本调用 `health --scheduled --output <临时路径>`，通过管道等待程序退出，读取输出文件时显式 UTF-8，不再解析本地代码页解码的 stdout。回读四个任务（daily/collect/parse/health），原子补充任务信息后通知。即使通知组件故障，原生健康结果仍可读取；通知失败应有独立错误结果，不能伪装为健康。

构建匹配 Debug Worker并放置固定 PDFium；运行 fmt、clippy、locked workspace tests、Windows 安装/健康脚本检查及独立发布包验收。全部通过后，构建同一生产包并保存源码补丁，备份并更新四个正式任务、只调整所需 Worker 路径，回读任务和有效配置、自检、包清单、报告哈希与账本。

显式人工 drain 处理现有积压，验证原件哈希、队列真实结果、失败/部分覆盖及模型调用零增量。手动健康通知用于落盘与上下文检查，不声称替代后续真实时间触发。后续五个工作日属于观察标准，不在本轮虚报为已经完成。
